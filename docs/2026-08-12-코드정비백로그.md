## 3. 항목별 상세

### A. `detector.dart`의 서버 주소 하드코딩 — 위험도 높음

**현상**
`lib/features/vision/data/detector.dart:62`가 서버 주소를 소스에 직접 기재한다.

```dart
static const String SERVER_URL = 'http://54.70.167.93:8000';
```

서버 주소를 참조하는 코드는 총 3개소인데, 나머지 2개소(`news_service.dart:13`, `route_repository.dart:15`)는 `dotenv.env['FASTAPI_BASE_URL']`을 읽는다. 이 파일만 예외다. 동일 라인은 `flutter analyze`에서 `constant_identifier_names` 위반으로도 검출된다.

**영향**
EC2 인스턴스 IP가 변경되면 객체 인식 기능만 조용히 실패한다. 다른 두 경로는 `.env` 변경으로 즉시 따라가므로 장애 원인 파악이 지연된다. 또한 감사 이력상 IP는 이미 한 차례 변경되었다 — `2026-07-01-프론트엔드현황.md:121`은 `35.161.165.53:8000`을 기록하고 있어, 현재 값과 다르다.

**조치 방향**
`SERVER_URL` 상수를 제거하고 `FASTAPI_BASE_URL`을 읽도록 전환한다. 상수명은 lowerCamelCase로 정정한다. `route_repository.dart:15`의 `_normalizeBaseUrl()`과 동일한 정규화 처리를 적용한다.

**대상 파일**
- `lib/features/vision/data/detector.dart:62`

### B. `main.dart`의 dotenv non-null 단언 — 위험도 높음

**현상**
`lib/main.dart:29`가 `dotenv.env['NAVER_MAP_CLIENT_ID']!`로 non-null 단언한다. `.env`에 키가 없거나 `.env` 파일 자체가 없으면 앱 시작 시 즉시 크래시한다.

현재 작업 트리에 `.env` 파일이 존재하지 않는다. `pubspec.yaml:95`가 `.env`를 에셋으로 선언하고 있어, `flutter analyze`는 `asset_does_not_exist` warning을 내고 `flutter test`는 에셋 번들 빌드 단계에서 중단된다(supplement 3-C).

**영향**
신규 클론 환경에서 앱과 테스트 모두 실행되지 않는다. 실패 지점이 초기화 코드가 아니라 에셋 번들 단계여서, 원인이 `.env` 부재라는 사실이 메시지에 드러나지 않는다.

**조치 방향**
`!` 단언을 제거하고 키 부재 시 명시적 오류 메시지를 출력하도록 변경한다. 별도로 `.env` 생성 절차가 `README.md`에 안내되어 있는지 확인한다(본 조사 범위 밖).

**대상 파일**
- `lib/main.dart:29`
- (연관) `pubspec.yaml:95`

### C. `widget_test.dart`가 Flutter 카운터 템플릿 원본 — 위험도 중간

**현상**
`test/` 하위 파일은 `widget_test.dart` 31줄 1개뿐이며, Flutter 프로젝트 생성 시의 카운터 템플릿이 그대로 남아 있다. 템플릿 주석(`:1-6`), 테스트명 `'Counter increments smoke test'`(`:14`), 카운터 0→1 검증(`:18-19, 26-28`), `Icons.add` 탭(`:23`)이 모두 원본이다. 패키지명만 `package:repo_jdh/main.dart`로 자동 반영되어 있다(`:11`).

**영향**
유효한 테스트가 0개다. 항목 B의 `.env` 문제를 해소하더라도 이 테스트는 두 가지 이유로 통과할 수 없다.

1. `MyApp`은 `ConsumerWidget`이고 앱은 `ProviderScope`로 감싸 실행되는데(`lib/main.dart:46, :49`), 테스트는 `ProviderScope` 없이 `pumpWidget(const MyApp())`를 호출한다(`test/widget_test.dart:16`).
2. 초기 라우트가 스플래시이며(`lib/core/router/app_router.dart:102`), 텍스트 `'0'`도 `Icons.add` FAB도 존재하지 않는다.

CI를 도입하면 첫 실행부터 실패한다.

**조치 방향**
삭제하거나, `ProviderScope`로 감싸 스플래시 렌더링을 검증하는 최소 테스트로 교체한다. 항목 B 해소가 선행되지 않으면 어느 쪽이든 실행되지 않는다.

**대상 파일**
- `test/widget_test.dart`

### F. provider 접근이 필요한 화면 위젯의 Consumer 미상속 — 위험도 중간

**재판정 근거**
해당 조항은 모든 위젯의 Consumer 상속을 요구하지 않는다. 따라서 **Riverpod provider를 읽어야 하는데 읽지 못하는 위젯**만 센다. 판정 기준은 다음 세 조건을 모두 만족하는 공개 위젯이다.

1. 파일이 data 레이어 Repository/Service를 직접 호출한다 (즉 provider 경유가 필요한 상태다)
2. 파일 전체에 `ref.watch` / `ref.read` / `ref.listen`이 한 번도 등장하지 않는다

## 5. 부록 — 두 감사 문서에 없는 추가 관찰

본 문서의 추출 범위(두 감사 문서) 밖이지만, 항목 E·F 재판정 과정에서 확인된 사항이므로 기록한다. 정비 항목 표에는 포함하지 않았다.

**개발용 더미·시드 코드가 릴리스 경로에 상시 포함되어 있다.**

`lib/core/dev/` 하위 3개 파일(566줄)이 data 레이어 6개 파일과 presentation 3개 파일에서 참조된다.

- 활성화 플래그는 모두 `static const bool ... = false`다 — `dev_data.dart:15` `DevData.enabled`, `dev_user.dart:12` `DevUser.enabled`, `group_service.dart:20` `_useDummy`. 따라서 더미 경로는 현재 실행되지 않는다.
- 그러나 시드 버튼 UI는 빌드 모드로 분기되지 않는다. `my_activity_screen.dart:203`은 `const _DevSeedButtons()`를 조건 없이 렌더링하며, 바로 위 `:202`에 "개발용 임시 버튼 — 배포 전 `_DevSeedButtons()` 삭제"라는 주석이 있다. `group_screen.dart:83`과 `group_feed_screen.dart:156-157`도 `DevSeed.seed*()` / `clear*()`를 호출한다.
- `kDebugMode` 사용처는 코드베이스 전체에 0건이다.

릴리스 빌드에서 사용자가 Firestore 데이터를 생성·삭제할 수 있는 버튼에 접근 가능한 상태다. 정식 출시 전 처리 대상이며, `docs/TODO.md`에는 등재되어 있지 않다.
