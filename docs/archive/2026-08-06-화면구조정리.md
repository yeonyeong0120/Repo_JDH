# 화면 구조 정리 (2026-08-06)

## 1. 작업 배경

제작설계서(SB) 작성 시 각 화면 슬라이드에 프로그램 ID(dart 파일 경로)를 기재한다. 문서에서 코드를, 코드에서 문서를 역추적하기 위함이다.

그 과정에서 화면 이름과 실제 역할이 어긋난 파일이 확인되었다. 파일명·클래스명이 그대로 SB에 실리므로, 문서 작성 전에 이름을 실제 역할에 맞게 정리했다.

프로그램 ID 표기 형식은 `lib/`와 `features/`를 생략한 3단 경로로 한다.

    plogging/presentation/plogging_tracking_screen.dart

이번 작업은 이름·파일 위치·import 형식만 다룬다. 동작은 바꾸지 않았다.

## 3. 변경하지 않은 것과 사유

이번 범위에서 제외하기로 확정한 항목이다. 정리 대상으로 보이더라도 손대지 않았다.

### (a) 개발용 시드 버튼 3곳

**무엇인지 / 어디에 있는지**

| 위치 | 내용 |
|---|---|
| `mypage/presentation/my_activity_screen.dart:1444` `_DevSeedButtons` | 가짜 활동 기록 심기(`:1492` `DevSeed.seedActivities()`), 지우기(`:1498` `DevSeed.clearActivities()`), 뱃지 판정 실행(`:1507` `BadgeService.checkAndSave()`) 3버튼. `:191`에서 화면에 배치된다. |
| `community/presentation/group_screen.dart:261` | 가짜 그룹 심기/지우기 2버튼(`:73` `DevSeed.seedGroups()` / `clearGroups()`). |
| `community/presentation/group_feed_screen.dart:780` | 가짜 피드 글 심기/지우기 2버튼(`:156` `DevSeed.seedPosts()` / `:157` `clearPosts()`). |
| `core/dev/dev_seed.dart` | 위 3곳이 호출하는 시드 유틸리티. |

**왜 남겼는지**

개발이 진행 중이라 팀 요청으로 유지한다. Firestore에 실데이터가 충분히 쌓이기 전까지 목록·그래프·뱃지 화면을 확인할 방법이 이 버튼뿐이다.

**나중에 판단이 필요한 점**

1. `my_activity_screen.dart:1500~1510`의 주석은 "원래는 플로깅 정산 화면에서 자동 호출됨"이라고 되어 있다. 이번에 확인한 결과 이 서술은 **사실이다**. `plogging/presentation/settlement_screen.dart:88`이 `_showBadgesIfAny()` 안에서 `BadgeService.checkAndSave()`를 호출한다(뱃지 획득 모달, 홈으로 나가기 직전). 다만 정산 화면은 플로깅을 실제로 완료해야 도달하므로, 버튼을 제거하면 개발 중 뱃지 판정을 수동으로 돌릴 경로가 사라진다. 제거 시점에는 정산 흐름이 정상 동작하는지 실기기에서 먼저 확인해야 한다. 확인 없이 제거하면 뱃지 획득 경로가 끊길 수 있다.
2. SB용 실기기 캡처 시 이 버튼이 화면에 찍힌다. 캡처 전에 임시로 숨기거나, 캡처 후 이미지에서 제외하는 처리가 필요하다.
3. 각 파일 상단의 `import 'package:repo_jdh/core/dev/dev_seed.dart';`에는 "배포 전 이 줄과 버튼 삭제" 주석이 이미 달려 있다. 배포 전 체크리스트에 이 3개 import를 검색 키로 넣어두면 누락을 막을 수 있다.
4. `core/dev/` 아래 `dev_user.dart`, `dev_data.dart`는 시드 버튼과 별개다. 6개 data 파일이 의존하므로 함께 지우면 안 된다.

### 4-4. as home_feature 별칭 제거

`app_router.dart`의 `as home_feature` 별칭을 제거했다.

`lib/` 전체에서 `class HomeScreen`은 `home/presentation/home_screen.dart:24` 한 곳뿐이며, `app_router.dart`가 import하는 다른 파일 중 `HomeScreen`을 노출하는 것은 없다. 엄밀히 말하면 `PloggingHomeScreen`과 `HomeScreen`은 애초에 식별자가 달라 충돌하지 않았으므로 이 별칭은 처음부터 컴파일상 필요하지 않았고, 사람이 읽을 때의 혼동을 막으려던 것으로 보인다. 리네임으로 그 혼동 자체가 사라졌다.

수정한 곳은 2곳이다.

| 이전 | 이후 |
|---|---|
| `import '...home_screen.dart' as home_feature;` (2줄) | `import '...home_screen.dart';` (1줄) |
| `builder: (context, state) => const home_feature.HomeScreen(),` | `builder: (context, state) => const HomeScreen(),` |

제거 후 `flutter analyze` 결과 이름 충돌은 발생하지 않았다(59 issues, error 0으로 동일).

### 4-5. build_runner

`flutter pub run build_runner build --delete-conflicting-outputs`를 마지막에 1회 실행했다. 변경된 파일은 `lib/core/router/app_router.g.dart` 하나뿐이고, 그 안에서도 소스 해시 1줄만 바뀌었다.

    -String _$appRouterHash() => r'7ece30dfe4311c98059d230cdde18bdc3f67430c';
    +String _$appRouterHash() => r'159e79b9120fb9a8f6044ead473efc3e60af4562';

이 프로젝트의 유일한 생성 파일이 `app_router.g.dart`이며, 이 파일은 화면 클래스를 전혀 참조하지 않는다. 따라서 이번 리네임에서 생성 파일이 실제로 깨질 여지는 없었다. 해시는 디버그 시 provider 재생성 감지에만 쓰인다.

## 5. 향후 예정

화면 ID가 확정되면 각 화면 파일 상단에 아래 형식의 주석을 부여할 예정이다.

```dart
/// Screen ID   : <확정된 화면 ID>
/// Screen Name : <화면 이름>
```

ID가 확정되기 전까지는 이 문서를 포함해 어디에도 임시 ID를 적지 않는다. 확정 전에 적어둔 ID는 확정 후의 실제 ID와 어긋나도 눈에 띄지 않는다.

다이얼로그·바텀시트는 해당 함수 위에 동일한 형식으로 붙인다.

이후 다음 명령으로 SB 화면목록과 대조한다.

```bash
grep -rn "Screen ID" lib/
```

## 6. 참고 기록 (이번 범위 밖)

아래는 이번 작업 중 확인했으나 손대지 않은 항목이다. 판단은 팀원에게 맡긴다.

**_TopBar 공용화**

`settings/presentation/notice_screen.dart:207`의 private 위젯. 주석은 "공지/FAQ/약관 공통 상단 바"라고 되어 있으나 private이라 실제로는 같은 파일 안에서만 공유된다. 결과적으로 동일한 뒤로가기 + 제목 패턴이 13곳에 인라인 중복 중이다(faq, inquiry, licenses, notice, terms, shop, coupon 목록/상세, activity_detail, activity_list, my_impact, profile, quest_list). `core/widgets/`에 이미 `app_button` 등 6개가 있어 승격 자리는 준비되어 있다.

**NewsArticle 모델 위치**

`NewsArticle` 모델이 `news/presentation/news_detail_screen.dart` 안에 정의되어 있다. 이 때문에 `news_service.dart`(data)와 `core/view_models/screen_views.dart`가 presentation 파일을 import하는 역방향 의존이 3건 발생한다. CLAUDE.md 2-2의 `presentation → domain → data` 단방향 규칙 위반이다. `news/domain/news_article.dart`로 추출하면 3건이 한 번에 해소된다.

**TrackingState / TrackingNotifier 위치**

`core/providers/tracking_provider.dart`에 있다. 트래킹은 plogging feature의 도메인이므로 `features/plogging/domain/`으로 옮길 여지가 있다. 옮기면 `PloggingTrackingScreen`을 `TrackingScreen`으로 더 줄이는 것도 자연스러워진다. 다만 `core`에 두면 feature 간 공유가 쉽다는 반대 논거도 있어 판단이 필요하다.

**feature 간 직접 import 27건**

가장 큰 원인은 `mypage`가 activity/impact 관련 data·domain 레이어를 갖지 않고 `plogging`에서 끌어 쓰는 구조다. `mypage/presentation`의 여러 화면이 `plogging/data/activity_service.dart`, `plogging/domain/activity_metrics.dart` 등을 직접 import한다. 구조 자체를 바꾸는 작업이므로 별도 논의가 필요하다.

**avoid_print 52건**

`firestore_repository`, `storage_repository`, `auth_repository`, `location_repository`에 집중되어 있다. `debugPrint`로 일괄 치환하거나 로깅 유틸을 도입하면 한 번에 해소된다. 이번에는 `camera_detection_screen.dart:121` 1건만 처리했다.

**test/widget_test.dart**

Flutter 기본 카운터 템플릿 그대로다. 이 앱에는 카운터가 없으므로 실행하면 실패한다. `flutter analyze`는 통과하므로 발견이 늦어질 수 있다. CI를 붙이기 전에 삭제하거나 실제 테스트로 교체해야 한다.

**_buildCircleButton 중복**

`plogging_tracking_screen.dart:32`의 `_buildCircleButton`이 `State` 클래스 밖 최상위 함수로 존재한다(`:504`, `:508`에서 사용). `route_setup_screen.dart:428`에 거의 동일한 `_circleButton`이 `State` 메서드로 중복되어 있다(`:144`에서 사용). 위 _TopBar 공용화와 함께 `core/widgets/`로 묶을 수 있다.

**shop_screen.dart:24 미사용 _category**

`unused_element` warning 1건. 필터 기능을 구현하다 만 흔적으로 보인다. 구현 예정이 없으면 삭제 대상이다.

**camera_detection_screen.dart의 ConsumerStatefulWidget**

`ref`를 전혀 쓰지 않으면서 `ConsumerStatefulWidget`을 상속한다(2-4절 참조). Riverpod 상태를 읽을 계획이 없다면 `StatefulWidget`으로 내릴 수 있다.
